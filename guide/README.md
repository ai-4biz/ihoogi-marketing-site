# iHoogi — מדריך AI חינמי למיקוד לקוח

יישום נפרד לפי האפיון ״אפיון מדריך AI חינמי למיקוד לקוח ← iHoogi (3)(1).pdf״,
עם הפתיחה הקצרה שנבדקה בשיחה עם רונה: ״במה העסק שלכם עוסק?״
כל הקוד תחת guide/; דף הבית והנכסים הקיימים אינם משתנים.

## מה נבנה

- הדרכה בעברית RTL, ללא הרשמה להתחלה; מותאמת גם לנייד.
- הסבר, שאלה אחת, אפשרויות ותשובה חופשית; כפתור עזרה.
- הקשר מתמשך דרך זיכרון קצר בשרת ושיקוף אישי, ללא שליחת כל ההיסטוריה בכל פעם.
- מטרה, שירות, צורך וקהל, חיוני מול עדיף, שאלות וכללי התאמה לאישור.
- מפת מיקוד לפני הרשמה, שמירה והעתקה, הדגמת שתי פניות מסומנות כבדויות.
- מעבר להצעת 50 פניות מדורגות במתנה, ללא אשראי וללא התחייבות.
- פרטי קשר, הסכמה להעברה בנפרד מהסכמה לשיווק, לוגו, אתר וצבע.
- תצוגה מקדימה של שאלון במיתוג שנבחר.
- API שרת בלבד ל־OpenRouter; מנגנון העברה מאומת עם מפתח idempotency.

## הרצה

Node.js 24 ומעלה. ללא חבילות חיצוניות:

```sh
cd guide
cp .env.example .env
# הגדירו מפתח ומודל במערכת הסודות; אין לצרף את .env לגיט.
node --env-file=.env server.mjs
npm test
```

נפתח ב־http://localhost:3080/guide/.
אין מפתח בקוד או בדפדפן. ללא הגדרות הממשק מסביר שה־AI אינו מחובר;
הוא אינו מחליף AI בתסריט דמה ואינו מציג הצלחה מדומה.

## עלות: יעד של פחות משקל לשיחה

- תקרת ledger של $0.12 לשיחה, עד 16 קריאות (כולל ניסיונות כושלים).
- תקרת ספק: $0.50 למיליון קלט, $3 למיליון פלט, ללא דמי בקשה/תמונה.
- מודל קבוע ב־GUIDE_MODEL; openrouter/auto חסום במדריך.
- שמירת עלות מקסימלית מראש, לפני בקשה; תקרה יומית משותפת נשמרת ב־SQLite.
- אין retry אוטומטי ואין החזר לתקציב אחרי כשל לא ודאי.
- שיחות וקלט ארוכים מוגבלים; קריאה שנכנסת מעבר לתקציב נחסמת לפני פנייה לספק.
- עד 1,100 טוקני פלט לשלב רגיל; עד 2,600 לאישור/סיכום.
- רק טקסט נשלח ל־AI. לוגו ואתרים מועברים לחיבור המערכת ולא מנותחים במודל.
- $0.12 × 6 ₪ לדולר × 1.15 מרווח עמלות = 0.828 ₪.
  זהו חישוב תקציבי, לא שער עדכני ולא התחייבות לעלות כוללת של אחסון, מסים או הודעות.
  איכות והעלות בפועל מחייבות הרצה במודל הנבחר. אין הבטחה שכל שיחה ארוכה תושלם בתוך התקרה.
- תמיכת max_price בהתאם ל־https://openrouter.ai/docs/guides/routing/provider-selection.

## מה עדיין לא הופעל

אין מפתחות AI בסביבת העבודה הזו, ולכן שיחה אמיתית עם ספק לא נבדקה.
לא נפרס האתר, לא שונה main ולא נוצרו לקוחות/לידים/הודעות במערכת חיה.
מקבל ההעברה בתוך iHoogi אינו קיים עדיין עבור החוזה הזה. מנגנון השליחה מוכן ונבדק
מול mock; אין לייחס לכך חיבור חי או יצירה אמיתית של שאלון.

## חוזה ההעברה למערכת

GUIDE_IMPORT_URL אינו שם ההגדרה: השמות בפועל הם IHOOGI_IMPORT_URL ו־IHOOGI_IMPORT_TOKEN.
ל־URL קבוע מהשרת נשלח POST עם Authorization ו־Idempotency-Key:

```json
{
  "schema_version": "ihoogi.focus-guide.v1",
  "idempotency_key": "sha256-of-session",
  "source": "focus-guide",
  "summary": {
    "goal": "...", "service": "...", "ideal_customer": "...",
    "customer_need": "...", "must_have": [], "nice_to_have": [],
    "marketing_message": "...", "insight": "...", "channels": [],
    "points_to_refine": [], "rules_approved": true,
    "screening_questions": [],
    "demo": []
  },
  "contact": {"name": "...", "email": "...", "phone": "..."},
  "brand": {
    "color": "#08675f", "websites": ["https://example.com"],
    "logo": {"name": "logo.png", "mime": "image/png", "base64": "..."}
  },
  "consent": {"transfer": true, "marketing": false, "accepted_at": "ISO-8601"}
}
```

מקבל ההעברה חייב לאמת סוד שרת ייעודי, להגביל גודל, לאמת שדות, ולמנוע כפילות
באופן עמיד גם מול בקשות מקבילות. הוא צריך להחזיר:

```json
{"status": "ready", "url": "https://ihoogi.com/verified-path"}
```

אם מדובר בתהליך המתנה מאומת: status=pending וקישור למערכת.
אין להחזיר ready לפני שהשאלון, המיתוג וכללי הדירוג נבנו בהצלחה.
לא נשלחים סיסמאות או מפתחות לדפדפן של המדריך.

## מיפוי לקוד האפליקציה שנבדק (main)

- profiles: primary_service, website, ideal customer fields require exact schema verification.
- questionnaires.meta.decision_context:
  serviceDescription ← service; idealCustomerDescription ← ideal_customer;
  goal=other; goalOther ← goal.
- questions: single_choice; question_text ← question;
  question_options.label/value ← options.label.
- questionnaires.meta.brand_logo_url הוא שדה מוכר.
- כללי התאמה אינם מקבילים אוטומטית ל־blueprint של המערכת.
  יש ליצור מיפוי למנגנון הדירוג בפועל ולבדוק בעזרת fixtures לפני שמאפשרים פרסום.
- provision-customer-from-lead מיועד לבעלים ולליד קיים מתוך שאלון מסוים.
  אין לקרוא לו מהמדריך הציבורי, לשנות הרשאותיו או ליצור ליד מלאכותי כדי לעקוף אותו.
- למשתמש קיים יש לדרוש כניסה לפני שינוי פרופיל/שאלון, ולא לזהות בעלות לפי מייל שהוזן.
- לוגו: לפענח מחדש/לנרמל תמונה במקבל, לשמור ב־Storage תחת בעלות מאומתת;
  URL של אתר הוא מידע בלבד ולא נשלפת ממנו כתובת בשרת (מניעת SSRF).
- יצירת משתמש חדש וחיבור אליו מחייבים מסלול הרשמה מאומת ושמירה על מדיניות המנויים.
- בדיקות כתיבה רק ב־staging/חשבון הבדיקה המורשה, לפי AGENTS.md של האפליקציה.

## אירוח ואבטחה

שרת זה מחייב דיסק SQLite עמיד ותהליך יחיד; אינו מתאים ישירות ל־GitHub Pages
או לפונקציה ללא דיסק עמיד. לפני הפצה ציבורית צריך לארח שרת מתאים או להעביר
את מאגר השיחות/תקציב למאגר טרנזקציוני עמיד עם נעילות.
השרת מאזין ל־127.0.0.1 לצורך בדיקה/Reverse proxy.
PUBLIC_ORIGIN חייב להתאים לכתובת הדפדפן. cookie הוא HttpOnly/SameSite/Secure ב־HTTPS.
הגבלת IP המקומית אינה מזהה לקוחות מאחורי proxy; לפני הפצה יש להגדיר trusted proxy
או rate limiting בשער, ולא לסמוך אוטומטית על X-Forwarded-For מהלקוח.
הגבלת מכסה למפתח OpenRouter משמשת שכבת הגנה נוספת.
נדרשים ניקוי שיחות ישנות, מדיניות פרטיות וניטור לפני הפצה.
